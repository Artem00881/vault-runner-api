# Vault Run — Provably-Fair Verification Guide

**Version:** 1.0  ·  **Date:** 2026-06-01

Vault Run's crash point is **provably fair**: it is fixed before a round starts
by a cryptographic commitment and can be independently verified afterwards by
anyone — no trust in our server required. This guide explains the scheme, how to
verify a round (by hand or in the browser), a fully worked example, and the
planned blockchain upgrade.

Source of truth: `src/fairness/crash.ts`, `src/fairness/seed-chain.ts`,
`src/fairness/salt.provider.ts`; in-browser verifier:
`vault-runner-main/src/lib/fairness.ts` and the `/fairness` page.

---

## 1. The two ingredients

Every round's crash multiplier is a deterministic function of two values:

1. **Seed** — a secret 32-byte value, drawn from a pre-committed **seed chain**
   (see §2). Revealed only after the round ends.
2. **Salt** — a chain-wide value mixed into every round's computation (see §4).

```
crash = f( HMAC_SHA256(key = seed, message = salt) )
```

The exact `f` (the 0.97/x curve) is in §5. Because the seed is **committed in
advance** and the salt is **fixed for the chain**, the operator cannot change a
crash after bets are placed.

---

## 2. Seed chain (commitment)

Seeds come from a hash chain (bustabit-style), built **backwards** so the head
can be published before any seed is used:

```
seed[n-1] = random 32 bytes
seed[i]   = SHA256( seed[i+1] )        for i = n-2 … 0
```

- **`seed[0]` is the public commitment** — published *before* any round in the
  chain is played (`GET /api/fairness/current`).
- Rounds consume `seed[1]`, `seed[2]`, … **in order**.
- Each seed stays secret until its round finishes, then is revealed
  (`GET /api/fairness/round/:id`).

**Why it's tamper-proof:** for any revealed round seed `seed[k]`, anyone can
check `SHA256(seed[k]) == seed[k-1]`, chaining all the way back to the public
commitment `seed[0]`. Since SHA-256 is one-way, the operator could not have
known or altered later seeds without breaking the chain — and the commitment was
public before play. (`verifyChainLink` in `seed-chain.ts`.)

---

## 3. Round lifecycle of a seed

1. **Before the chain:** `seed[0]` (commitment) is published.
2. **Round k betting opens:** the crash is *already* determined by `seed[k]` +
   salt, but `seed[k]` is still secret — neither players nor (verifiably) the
   operator can act on it.
3. **Round k ends:** `seed[k]` is revealed.
4. **Anyone verifies:** recompute the crash from `seed[k]` + salt, and check the
   chain link back to the commitment.

Revealed history is queryable per round, so the full chain can be audited after
the fact.

---

## 4. The salt

The salt is mixed into every round's HMAC so seeds alone don't reveal crashes
prematurely. `SaltProvider` is an interface (`salt.provider.ts`) — swapping it
changes the **trust model** without touching any other fairness code:

- **Now (demo / play-money): `DailySaltProvider`** — a fresh random salt,
  committed per chain. Operator-published; standard provably-fair trust.
- **Planned (real money): `BlockHashSaltProvider`** — see §7.

---

## 5. Crash formula

From `crash.ts` (BigInt throughout — no float bias):

```
E      = 2^52
FACTOR = 97                                   // 100 · (1 − 0.03 house edge)
h      = first 13 hex chars of HMAC_SHA256(seed, salt)   // 52-bit int [0, 2^52)
cents  = floor( FACTOR · (E + 1) / (h + 1) )
cents  = clamp(cents, 100, CAP)               // 1.00x … cap
crash  = cents / 100
```

This realises `P(crash ≥ x) = 0.97 / x` (RTP 97%); see `game-math-spec.md` and
`simulation-report.md`.

> **HMAC input encoding (read this before re-implementing).** The HMAC **key** is
> the 32-byte seed, **hex-decoded** (`Buffer.from(seedHex, "hex")`); the HMAC
> **message** is the salt as a **UTF-8 string** — the literal characters, **NOT**
> hex-decoded (`crash.ts:33` `…update(salt)`). For a block-salt epoch the salt is the
> `0x…` block-hash string exactly as published. Hex-decoding the salt produces a
> different (wrong) crash — see the note under the worked example in §6.

## 6. Worked example (real values)

A 4-seed chain with a sample salt. Round 1 consumes `seed[1]`:

```
Commitment seed[0] : 0e78d287ff6bc77104c9488b5d50f5971cd673701018aa6f12792cbcf8308f1b
Salt               : a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f90

Round 1 revealed seed[1]:
  23616c071639ce56cff330ad9300cabfaca163b1475b7d820e53b3321692cf1b
  → crash = 3.27x
```

**Verify it yourself (two checks):**

1. **Chain link** — confirm the revealed seed belongs to the committed chain:
   `SHA256(seed[1])` should equal the commitment `seed[0]`:
   ```
   SHA256(23616c0716…1692cf1b) = 0e78d287ff…f8308f1b   ✓ matches seed[0]
   ```
2. **Crash recompute** — `HMAC_SHA256(key = seed[1], msg = salt)`, take the first
   13 hex chars as `h`, apply §5 → **3.27x**.

Both checks pass with no access to our server. (Generated by the production
functions; reproduce with `computeCrash` + `verifyChainLink`.)

> **Encoding note (must read to reproduce 3.27x).** In step 2 the salt above is fed
> to the HMAC as a **UTF-8 string** (its literal 64 characters), while the seed is
> **hex-decoded** to 32 bytes — exactly as in §5 / `crash.ts:33`. With that encoding
> the crash is **3.27x**. If you instead hex-decode the salt (it *looks* like hex),
> you get a different result (**1.22x**) — that is the most common re-implementation
> mistake, not a discrepancy in the math. The chain-link check in step 1 passes
> either way, so always cross-check the crash with the documented encoding.

## 7. How to verify in practice

- **In the browser (no tools):** open the **`/fairness`** page on the game.
  Paste the round's revealed seed + salt → it recomputes the crash live using
  Web Crypto + BigInt (`vault-runner-main/src/lib/fairness.ts`), the *same*
  formula as the server. It also checks the chain link.
- **Via API:**
  - `GET /api/fairness/current` — the active chain's public commitment.
  - `GET /api/fairness/round/:id` — a finished round's revealed seed + salt +
    server-recomputed crash + `linkVerified`.
  - `POST /api/fairness/verify` `{ seed, salt, prevSeed? }` — recompute a crash
    (and optionally check a chain link) server-side, for cross-checking.
- **Offline / any language:** implement §2 + §5 (SHA-256 and HMAC-SHA256 are in
  every standard crypto library). Our browser verifier is open and copyable as a
  reference implementation.

## 8. Blockchain-anchored salt (grind-proof) — IMPLEMENTED

The salt can be the hash of a **future finalized Ethereum block**, making crash
points **grind-proof**: the operator cannot pre-search seeds for a favourable
salt because the salt does not exist yet when the chain is committed.

**Epochs.** The seed chain is split into epochs (`FairnessChain`). Each epoch is an
independent provably-fair chain with its own public commit (`seed[0]`) and its own
salt. When an epoch runs out the engine rolls over to the next one — no stall.

**How a block-salt epoch is committed and revealed:**

1. **Commit (before the block exists):** a new epoch publishes (a) its chain head
   `seed[0]` and (b) a **target Ethereum block height** = current finalized head +
   `ETH_SALT_LEAD_BLOCKS` (default 10). Both are visible in advance at
   `GET /api/fairness/current` → `nextEpoch` (status `pending`).
2. **Arm (after the block finalizes):** once that block is **finalized**, its hash
   becomes the epoch's salt (status `armed`). Finalized blocks are reorg-safe — the
   value can never change. The oracle cross-checks the hash across several public
   Ethereum RPCs and requires agreement, so no single endpoint can spoof it.
3. **Serve & reveal:** when the previous epoch ends, the armed epoch becomes
   `active` and serves rounds. Each round still reveals its seed on crash, and
   anyone recomputes `crash = f(HMAC_SHA256(seed, salt))` with `salt` = the public
   block hash — checkable against any Ethereum explorer.

Because the chain head was committed **before** the target block existed, neither
the operator nor a player could have ground the seeds against the salt.

**Reliability.** If the salt isn't available when an epoch must start (cold start,
or an oracle outage), the engine falls back to a **random** salt for that epoch
(transparently — `saltSource: "random"`) so the game never stalls, and resumes
block-salt epochs as soon as the oracle recovers.

**Verify a block-salt round:** take the round's revealed `seed` + the epoch's
`salt`, confirm `salt` equals the published Ethereum block's hash (e.g. on a block
explorer), then recompute the crash (§5) — exactly as in §7.

**Implementation:** `src/fairness/eth-block.ts` (finalized-block oracle, multi-RPC
agreement), `EthBlockSaltProvider` in `salt.provider.ts`, epoch orchestration
(pending → armed → active) in `fairness.service.ts`. Enabled with
`SALT_PROVIDER_TYPE=eth-block`. Optional add-on (future): a **per-player client
seed** folded into the HMAC for extra individual assurance.

> **Status:** §1–§7 describe the core scheme. §8 (block-hash salt) is **built and
> validated against Ethereum mainnet** (2026-06): a real future block was committed
> in advance, armed with the real finalized hash, and served verifiable rounds. The
> play-money demo runs the random-salt provider by default; block-salt is one env
> flip (`SALT_PROVIDER_TYPE=eth-block`) away. Player verification UX is identical
> either way — only the salt source and trust guarantee improve.

---

## 9. Summary

- Crash = `f(HMAC_SHA256(seed, salt))`, fixed before the round by a public
  commitment.
- Seeds form a SHA-256 chain whose head is published in advance → no seed can be
  altered or front-run.
- Anyone can recompute any finished round's crash and check the chain link, with
  zero trust in our server (browser page, API, or offline).
- Real-money upgrade anchors the salt to a future block hash, making the result
  grind-proof — same verification UX, stronger guarantee.
